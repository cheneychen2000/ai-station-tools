"开启缓存能省 90% 输入成本"这类说法在营销页上很常见，但它省略了三个前提：前缀要足够大、命中要足够频繁、写入费要能摊平。这三件事里任何一件不成立，缓存不但不省钱，还会更贵——因为写入缓存本身是有代价的。

这篇不谈"如何开启"，而是把收益条件算清楚。文中涉及的两家厂商机制细节，均来自 2026-10-31 实际访问的官方文档与定价页；OpenAI 与 Google 的对应文档在本次核验中无法访问（平台对抓取返回 403 与超时），因此本文**不引用**这两家的门槛数值与计费倍率，需要时请以官方文档为准。单价不在此处罗列，统一以 [模型库](/models/) 的核验价与厂商定价页为准。

## 一、缓存命中的是前缀，不是"相似内容"

大模型推理时的注意力计算需要历史 Token 的中间结果（KV 缓存）。如果两次请求的开头部分逐 Token 相同，这部分中间结果可以复用，不必重算——这就是 Prompt Caching 的全部原理。它带来的直接结果是：缓存判定是**前缀逐字匹配**，不是语义相似。

理解这一点就够了，剩下的性质都能推出来：前缀里改一个字，后面全部失效；把动态内容放在中间，等于把它后面的所有内容都变成"每次都变"；把动态内容放在最后，前面的稳定部分才有机会命中。

## 二、两家厂商的实际机制差别很大

不同厂商的缓存不是同一套协议，把 A 家的经验套到 B 家会得出错误结论。目前可核验的两种典型形态：

**DeepSeek：默认开启的硬盘前缀缓存。** 官方文档写明它对所有用户默认启用、无需改代码，每次请求都会触发缓存构建；由于采用滑窗注意力，每个缓存前缀是一个**独立完整的单元**，命中要求"完全匹配某个已持久化的前缀单元"，而不是部分重叠。缓存单元在三种时机被持久化：请求边界（用户输入结束位置与模型输出结束位置各一个）、系统检测到的公共前缀、以及长输入/长输出按固定 Token 间隔切分。文档还明确了两件事：缓存是 best-effort，不保证命中；不再使用后自动清除，生命周期通常是几小时到几天。

这两条对工程的影响很具体。多轮对话天然命中——第二轮请求的前缀恰好等于第一轮"输入 + 输出"这个单元。而"同一段长文档 + 不同提问"的形态**第一轮、第二轮都不命中**（因为各自的前缀单元不同），要到系统把公共前缀单独持久化之后才可能命中。也就是说，`长文档 + 问题` 的模板在前两次调用上是拿不到折扣的。

**Anthropic：显式缓存，写入单独计价。** 官方定价页把"缓存读取"与"缓存写入"列为独立价格行，并注明缓存价格以 **5 分钟 TTL** 为基准、另有延长缓存的选项。以页面列出的 Haiku 5.5（≤100K 档）为例，缓存读取价约为输入价的 1/10，缓存写入价约为输入价的 1.25 倍。倍率关系比绝对数字更值得记住：**读便宜一个数量级，写贵四分之一**。

（OpenAI 与 Google 的缓存同样存在，但本次未能核验其门槛与计费细节，不做描述。）

## 三、盈亏平衡：写入费什么时候回本

把上面的机制抽象成四个量：稳定前缀 Token 数 `S`、动态部分 Token 数 `D`、未命中输入单价 `P`、请求次数 `n`。设缓存读取价为 `r·P`（`r < 1`），写入价为 `w·P`（`w ≥ 1`），写入次数为 `W`，命中次数为 `H = n − W`。

无缓存时，输入成本是 `n·(S + D)·P`。

有缓存时：写入的那 `W` 次付 `w·S·P`，命中的 `H` 次付 `r·S·P`，动态部分每次都付 `D·P`。两者相减，动态部分抵消，净节省为：

```
节省 = S · P · [ n·(1 − r) − W·(w − r) ]
```

由此得到两个结论，都不依赖 `D` 的大小：

**其一，缓存收益与动态内容无关，只取决于稳定前缀的体量。** 前缀只有 200 Token 的请求，即使命中率 100%，省下的绝对值也微不足道——这类场景该优化的是 prompt 本身，不是缓存。

**其二，一次写入需要被命中多少次才能回本。** 把 `H = n − W` 代回节省式，整理成"每次写入需要多少命中"：

```
节省 = S·P·[ n(1 − r) − W(w − r) ] > 0
     ⇔ (W + H)(1 − r) > W(w − r)
     ⇔ H / W > (w − 1) / (1 − r)
```

也就是说，**每写入一次，至少要有 `(w − 1)/(1 − r)` 次命中才划算**。把两家的倍率代进去：

| 形态 | `r`（命中价/输入价） | `w`（写入价/输入价） | 每次写入所需命中数 |
|---|---|---|---|
| 显式缓存（写入单独计价） | 0.1 | 1.25 | `(1.25−1)/0.9 ≈ 0.28`，即写 1 次后命中 1 次就足够回本 |
| 默认前缀缓存（无写入费） | 0.02 | 1（写入按普通输入计） | `0`，即只要有一次命中就是净赚 |

第二行解释了一个常见困惑：默认开启的缓存为什么"看起来几乎免费"。它的写入成本等于"这次请求本来就该付的输入价"，没有额外附加费，所以只要后续有任何一次命中就是净赚。第一行则提示了另一种风险：**如果前缀每次都失效**（`W = n`、`H = 0`），收益变成 `S·P·n·(1 − w) < 0`——你为每次请求多付了 25% 的输入成本，而且还拿不到命中。这就是"开了缓存反而更贵"的完整解释。

所以做缓存优化的第一步不是改 prompt，而是估算 `n`：同一个前缀在你的业务里会被复用几次。一次性任务（生成一份报告、翻译一篇文档）不值得做缓存；同一份系统提示词被几千次调用复用的客服机器人，才值得。

## 四、前缀稳定性：六种把缓存打死的写法

收益公式里的 `W` 是唯一的杠杆。以下是工程上最常见的几种破坏方式，都发生在"以为没什么影响"的地方：

1. **时间戳进系统提示词。** `当前时间：2026-10-31 14:03:22` 出现在第一行，等于每一秒都是一个新前缀。要当前日期就放到用户消息里，或者精确到天并接受一天一次失效。
2. **用户 ID、会话 ID、请求 ID 拼在 prompt 开头。** 常见于"你正在为 {user} 服务"这类模板。把它们移到末尾，或改用元数据传递。
3. **few-shot 示例随机打乱顺序。** 每次请求从示例池里随机抽三个、顺序还不固定，前缀就不可能稳定。要么固定顺序，要么把它们放在动态区。
4. **工具定义每次重新生成。** 函数列表按 `Object.keys()` 的插入顺序序列化，不同代码路径顺序不同；或者每次请求都带上"可选工具"的子集，前缀都会变。工具定义固定顺序、固定集合，是最省事的优化。
5. **JSON 序列化的键顺序不稳定。** 把结构化上下文 `JSON.stringify` 进 prompt 时，键顺序取决于对象构造方式。要么稳定排序，要么用固定的模板拼接。
6. **在中间插入而非末尾追加。** 多轮对话里"插一条系统提醒"会把后面的全部内容推离已有前缀。追加到末尾、或作为独立的最后一条消息。

反过来说，一个稳定前缀该长什么样：固定的角色与规则 → 固定的输出格式约束 → 固定的示例 → 固定的工具定义 → 分隔标记 → 动态内容。**顺序本身就是缓存设计**：越稳定越靠前。

```ts
export interface PromptParts {
  role: string;                 // 稳定
  rules: string[];              // 稳定
  formatSpec: string;           // 稳定
  examples: Array<{ q: string; a: string }>; // 稳定且顺序固定
  toolSchemas: string[];        // 稳定且顺序固定
  dynamic: { today: string; userId: string; question: string; context: string };
}

/** 把稳定部分拼成固定前缀，动态内容一律放在末尾 */
export function buildPrompt(p: PromptParts): Array<{ role: 'system' | 'user'; content: string }> {
  const stable = [
    p.role,
    ...p.rules,
    `输出格式：${p.formatSpec}`,
    p.examples.map(e => `示例输入：${e.q}\n示例输出：${e.a}`).join('\n\n'),
    p.toolSchemas.join('\n')
  ].join('\n\n');

  const dynamic = [
    `日期：${p.dynamic.today}`,          // 放在动态区，不污染前缀
    `用户：${p.dynamic.userId}`,
    `参考资料：${p.dynamic.context}`,
    `问题：${p.dynamic.question}`
  ].join('\n');

  return [
    { role: 'system', content: stable },
    { role: 'user', content: dynamic }
  ];
}
```

这个结构有个副作用需要提前接受：动态区里的参考资料如果很长，它本身也不会被缓存。所以"一份大文档 + 多个问题"的正确做法是**把文档放进稳定前缀**、问题放动态区，这样第二个问题开始就能命中；而不是把文档和问题一起塞在动态区。

## 五、命中率不等于成本降幅

这是最容易被误读的一步。假设缓存让输入单价降了 90%，你的总账单并不会降 90%，原因有两层：

**第一层：缓存降的是输入，而输入往往不是账单的主体。** 按本站 [定价比较指南](/guides/llm-api-pricing-comparison/) 的示例用量（输入 2000 / 输出 800 / 命中率 30%）复算，本站收录的模型中输出项占月成本的比例落在 **54%~77%** 之间（可以自己在 [成本计算器](/cost/) 里勾选几个模型验证这个区间）。换句话说，即使输入成本归零，总账单也只能降四分之一到一半——"省 90%" 指的是单价，不是账单。

**第二层：命中率是平均值，成本是加权值。** 真实业务里请求长短差异很大，用"总命中 Token / 总输入 Token"算出来的比例，会被少数超长请求主导。更有意义的指标是按请求统计命中率分布：有多少比例的请求命中了 0%、有多少命中 80% 以上。一个 P50 命中率 70%、但最贵的那批长请求命中率为 0 的系统，成本改善会远低于预期。

把两层合起来的换算公式：

```
总成本降幅 ≈ 输入成本占比 × 输入单价降幅
输入单价降幅 = (1 − r) − (W/n)·(w − r)
```

代入显式缓存的倍率（`r=0.1`、`w=1.25`）与"全部命中"（`W/n = 0`），输入单价降幅上限是 90%；若每次都写入，降幅变成 `0.9 − 1.15 = −0.25`，即**成本上升 25%**。这两个极端之间，决定了你是省钱还是亏钱。

## 六、怎么测：从 usage 里算命中率

不要用"我觉得前缀挺稳定的"判断命中率，用响应里的用量字段算。字段名各家不同，DeepSeek 的输入侧拆成命中与未命中两个字段，两者之和即本次输入总量：

```ts
export interface UsageLike {
  prompt_cache_hit_tokens?: number;
  prompt_cache_miss_tokens?: number;
  prompt_tokens?: number;
}

/** 返回 [0,1] 的命中率；字段缺失时返回 null，绝不默认成 0 或 1 */
export function cacheHitRate(usage: UsageLike): number | null {
  const hit = usage.prompt_cache_hit_tokens;
  const miss = usage.prompt_cache_miss_tokens;
  if (typeof hit === 'number' && typeof miss === 'number' && hit + miss > 0) {
    return hit / (hit + miss);
  }
  if (typeof hit === 'number' && typeof usage.prompt_tokens === 'number' && usage.prompt_tokens > 0) {
    return hit / usage.prompt_tokens;
  }
  return null;
}
```

`null` 的处理很关键：字段不存在意味着"这家厂商不拆分统计"或"这次调用没有缓存信息"，而不是"命中率为 0"。把它当成 0 会让你误判优化无效，进而做出错误决策（例如放弃一个其实有效的结构改造）。

监控上建议看三个数：命中率的分位数分布、稳定前缀的 Token 占比（`S / (S+D)`）、以及"连续未命中的请求比例"。最后这个指标能直接指出前缀是否被某个变量反复打破。

## 七、什么情况下不该做缓存

- **一次性任务**：`n = 1`，只有写入没有命中，纯亏。
- **前缀天然短**：系统提示词只有一两百 Token，节省绝对值可以忽略，优化力气应该花在减少输出上。
- **前缀频繁失效**：内容本身按请求变化（每次都要注入不同的用户档案、不同的检索结果在开头），先改结构，改不动就不要开缓存。
- **输出主导的任务**：长文生成、代码补全，输入本来就小，缓存对总成本的影响被输出单价稀释。
- **对有最小可缓存长度的厂商**：前缀低于门槛根本不进缓存（各家门槛不同，以官方文档为准），小前缀的请求不要指望命中。
