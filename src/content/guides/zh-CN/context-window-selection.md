选上下文窗口时，多数人的做法是打开一张"模型规格对比表"，选窗口最大的那个。这个决策方式有两个问题：窗口是模型规格里最便宜的资源（几乎所有主流模型都在往百万级走），而它同时是最容易被浪费的资源（每次请求都为整段历史付费）。

真正需要回答的不是"哪个窗口大"，而是"我的请求实际有多长、留多少给输出、剩下的历史怎么处理"。

## 一、三个长度别混为一谈

官方规格里出现的数字至少有三个，含义完全不同：

| 指标 | 含义 | 超出的后果 |
|---|---|---|
| 上下文窗口 | 单次请求输入 + 输出的总上限 | 请求被拒（通常是 400 类错误） |
| 最大输出 | 单次生成的上限 | 被截断，或请求被拒 |
| 可用输入 | 窗口 − 输出预留 − 系统提示/工具定义占用 | 你实际能塞进去的文档量 |

第三个才是工程上真正可用的数。一个 1M 窗口的模型，如果每次要预留 8K 输出、系统提示与工具定义占 3K，你能放资料的空间是 1013K 左右；再加上多轮对话的历史每轮都在增长，实际可用量还会继续缩水。

以官方文档为例：DeepSeek 的两个在售模型均为 1M 上下文、最大输出 384K（2026-10-31 核验）；Claude 的定价页只写"最高 1M，因模型而异"，并在 Haiku 5.5 上给出 100K 提示为界的档位。可见"窗口 1M"是个上限陈述，不是"你每次都能塞 1M 而且价格不变"的承诺。

## 二、先量，再选

在没有数据的情况下讨论窗口大小，讨论的是别人的业务。你需要四个统计量，全部能从自己的日志里拿到：

- **单次输入的 P50 与 P95**：决定你落在哪个档位；
- **输入的长度分布形态**：是集中在 2K 附近，还是有 5% 的请求超过 200K？后者往往决定成本，前者决定体验；
- **输出 Token 的 P95**：决定要为输出预留多少窗口；
- **多轮会话的轮数分布**：决定历史治理策略。

一种常见的长尾形态（描述形状，不是统计结论）：绝大多数请求输入在几 K 以内，但少数请求夹带一份完整文档，长度高出两个数量级。这批长请求会独占绝大部分成本——如果只看平均值，你会得出"我们用量很小"的结论。去自己的日志里量一次，多半能看到类似的尾巴。

用 [成本计算器](/cost/) 时也要按这个思路填：不要填平均输入，填 P95，并单独算一遍"最长那批请求"的成本。两个结果差距大的话，你的优化目标就明确了——把长请求单独治理，而不是给全体换模型。

## 三、长上下文与检索的成本翻转点

"窗口够大就能整段塞"在技术上成立，在成本上要算一笔账。

设文档总量 `L` Token，每次请求的系统提示 `S`，检索片段共 `k·c`（`k` 条、每条 `c` Token），请求次数 `n`：

```
整段注入：n × (L + S)
检索注入：n × (S + k·c)  +  一次性索引成本 E
```

因为检索侧每次只付 `k·c`，而整段注入每次都要重付 `L`，只要 `L` 显著大于 `k·c`、且 `n` 大于 1，检索就是更便宜的。翻转点出现在 `n` 很小、`E` 很大的时候——也就是"只问一次"的场景：为一次提问建一套索引，工程与基础设施成本远超省下的 Token。

这就给出一个清晰的分界：

| 形态 | 建议 |
|---|---|
| 一次性分析（一份合同、一份财报，问 1~3 个问题） | 整段注入，前提是长度在窗口内且不跨档 |
| 同一批资料被反复提问（客服知识库、内部文档问答） | 建索引走检索，或至少把资料放进稳定前缀享受缓存 |
| 资料每天变、问题也每天变 | 增量索引 + 检索，整段注入会同时贵且慢 |
| 需要跨文档聚合（"这些合同里风险条款有哪些"） | 检索 + 二次归纳，整段注入容易读到一半就超窗口 |

还有一个必须自己验证的假设：**长上下文不等于同等质量**。窗口能装下，不代表模型能把 20 万字里的关键细节都用到。要确认这件事，唯一可靠的做法是拿你自己的问题集做 A/B：整段注入 vs 检索片段，比较答案的事实正确率与遗漏率。本文不引用任何未经核实的召回率结论，因为这类数字高度依赖任务与文档结构。

## 四、分档边界制造的"价格台阶"

按输入长度分档计价的模型，档位是台阶而不是斜坡：单次输入一旦越过边界，整次请求的单价跳到高档。本站 [模型库](/models/) 目前收录的分档模型里，边界分别落在 100K、272K、512K 附近（例如 MiniMax M3 以 512K 输入为界、Claude Haiku 5.5 以 100K 提示为界、部分模型的 >272K 长上下文档官方未公布费率，档案页标为"未公开"并拒绝估算）。这些边界与费率请以档案页标注的核验日期为准。

跨档的代价要用总价算，而不是用单价算。假设低档单价 `P`、高档 `P'`（`P' > P`），单次输入 `L` 恰好跨过边界 `B`：

```
跨档前后成本比 = P'·L / (P·L) = P'/P
```

也就是说，一旦跨档，你为**全部输入**付高档价，而不只是超出 `B` 的那部分。于是"再多放 5% 的资料"可能让成本跳 2~5 倍。工程上的对策很朴素：在组装 Prompt 时做一次长度检查，接近边界就先裁剪或拆成两次请求，而不是让它自然溢出。

这也是"最大输出"会影响成本的地方：如果输出被截断需要重发一次，你会为同一份输入付两遍钱。与其省那点窗口，不如把输出预留充足。

## 五、多轮历史怎么处理

多轮对话的输入随轮数增长——每轮都要把之前的全部消息重新发送。四种治理策略的取舍：

| 策略 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 全量携带 | 保留全部历史 | 上下文最完整 | 输入随轮数线性增长，长会话迅速变贵 |
| 滑动窗口 | 只带最近 N 轮 | 成本可控、实现简单 | 早期约定会丢，用户会觉得"它忘了" |
| 摘要压缩 | 定期把旧历史压成摘要 | 保留要点、增长可控 | 摘要本身要调用一次模型，且可能丢细节 |
| 检索化 | 历史落外部存储，按需检索 | 会话可以无限长 | 工程复杂度最高，检索失败会答非所问 |

选择依据是"早期信息对当前问题还有多大用"。客服工单、代码调试这类**状态累积型**会话，早期信息（报错原文、已排除的原因）非常关键，滑动窗口会直接毁掉体验；闲聊、问答这类**话题漂移型**会话，保留最近几轮就够。

一个低成本折中：**固定区 + 滑动区**。把不变的部分（角色、规则、关键事实、工具定义）放固定区，把最近 N 轮放滑动区，中间的历史压成三五条要点。这套结构还有个附带好处——固定区在前、内容稳定，天然适合前缀缓存。

## 六、四类场景的具体建议

**文档分析。** 优先确认文档是否跨档；跨档时先考虑"分段读 + 汇总"，而不是硬塞。分段读的代价是多次调用，需要比较 `整段一次` 与 `分 N 段 + 一次汇总` 的总 Token。

**RAG。** 窗口大小不是主要矛盾，`Top-K × 片段长度` 才是。8 条 500 Token 的片段已经占了 4K 输入，把 K 提到 30 通常不会让答案更好，只会让账单更贵。

**Agent。** 窗口要按"最长步数"预留，而不是按首步。多步任务的历史单调增长，第 20 步的输入可能是第 1 步的十倍以上；窗口不够时表现为任务中途失败，而失败后重跑会让成本翻倍。

**代码分析。** 代码的 Token 密度高（缩进、括号、标识符都吃 Token），同样的字符数下比散文占更多窗口。估算时按实测分词结果，不要按行数折算。

## 七、一个六步决策流程

1. **量输入**：从日志取 P50 / P95 / 最大值，以及长度分布形态；
2. **算可用输入**：窗口 − 输出预留 − 系统提示与工具定义，得到真正能放资料的空间；
3. **判断是否跨档**：若 P95 落在档位边界附近，先做裁剪或分段，别让它自然溢出；
4. **算两种方案的总价**：整段注入 vs 检索/分段，代入自己的请求次数；
5. **验证质量**：在自有问题集上对比两种方案的答案正确率，别只看成本；
6. **确定历史策略**：按会话类型选全量/滑动/摘要/检索化，并写进 Prompt 组装代码，而不是靠调用方自觉。

## 八、关于规格核验

上下文窗口与最大输出属于高时效数据，各厂商会用"最高值 + 因模型而异"的方式表述，第三方整理稿经常落后于官方。本站的处理方式是：规格与价格只来自官方页面，逐条标注核验日期，未公布的值标为"未公开"而不是填一个看起来合理的数字（口径见 [定价方法论](/pricing-methodology/)）。你在做容量规划时，请以 [模型库](/models/) 档案页标注的核验日期为准，并在正式启用前回到官方页面确认一次；本文引用的两处官方表述核验于 2026-10-31。

窗口不是越大越好，也不是越小越省。它是你为"这一次请求要带多少历史"付的租金——先量清楚要带多少，再决定租多大的房子。
