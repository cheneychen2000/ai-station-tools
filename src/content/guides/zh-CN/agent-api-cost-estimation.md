给 Agent 做预算时最常见的错误，是把它当成"一天调用 N 次"的普通问答接口。实际上一次 Agent 任务就是一次自我迭代的循环：每一步都要重新发送全部历史，每多一步、下一次的输入就更长一分。步数上去之后，账单涨得比线性快得多。

这篇给出可以手算的成本模型。文中所有数字都是**明确的示例假设**，不是任何客户的实测数据，也不是行业统计；代入你自己的参数就能重算。

## 一、一次任务 = 若干次模型调用 + 若干次工具执行

把一次任务展开，成本由四块构成：

| 构成 | 计费方式 | 变化特征 |
|---|---|---|
| 模型调用 | 输入 Token + 输出 Token | 步数越多、单步输入越长 |
| 工具执行 | 外部服务按次/按量计费，或自建服务的算力 | 与工具调用次数成正比 |
| 上下文携带 | 历史消息、工具返回、记忆片段都算输入 | 每步重复发送，随步数增长 |
| 失败与重试 | 同一段内容被重复计费 | 概率事件，但期望值稳定 |

第三项是 Agent 与单轮问答的根本差异：单轮问答的输入是"系统提示 + 用户问题"，Agent 的输入是"系统提示 + 到目前为止发生的全部事情"。

## 二、上下文增长的平方效应

设：

- `S` = 每步都带的固定部分（系统提示、工具定义、记忆摘要），Token；
- `o` = 每一步新增的内容量（模型输出 + 工具返回结果），Token；
- `n` = 步数（一次模型调用算一步）。

第 `i` 步（`i` 从 0 开始）的输入是 `S + i·o`。把 `n` 步加起来：

```
总输入 = Σ(S + i·o) = n·S + o·n·(n−1)/2
总输出 = n·o
```

那个 `n²` 项就是全部问题的来源。它意味着：**当上下文承载的历史成为主导项时，步数翻倍会让输入成本接近四倍**。这也直接给出了优化优先级——把 30 步压到 15 步，比你换一个便宜 50% 的模型更有效。

用一个直观的对比说明"朴素估算"偏差有多大。朴素估算指"步数 × (S + o)"，也就是假定每步输入长度不变：

| 场景 | 步数 n | S | o | 朴素估算输入 | 分步累计输入 | 低估倍数 |
|---|---|---|---|---|---|---|
| 简单（单工具调用） | 4 | 1,500 | 300 | 7,200 | 7,800 | 1.08× |
| 典型（检索 + 规划 + 多轮工具） | 12 | 2,000 | 400 | 28,800 | 50,400 | 1.75× |
| 复杂（长任务、多工具、代码执行） | 30 | 2,500 | 450 | 88,500 | 270,750 | 3.06× |

校验一下典型场景：`12 × 2,000 + 400 × 12 × 11 / 2 = 24,000 + 26,400 = 50,400`。复杂场景：`30 × 2,500 + 450 × 30 × 29 / 2 = 75,000 + 195,750 = 270,750`。

结论很直接：**步数在 10 以内，线性估算还能用；步数超过 20，必须按分步累计算。** 而现实中的编码类、研究类 Agent，20 步是常态而不是上限。

## 三、工具执行：模型之外的第二本账

工具费用有两个来源，性质完全不同：

**模型侧**：工具的参数 Schema 属于输入 Token，工具调用的参数与返回结果进入后续每一步的输入。挂 20 个工具、每个描述写三段话，每步输入就白白多出几千 Token，而这份开销在每一步都重复。

**服务侧**：工具真的执行时，可能产生模型之外的费用。最典型的是联网检索类工具——DeepSeek 的价格页把 Search 与 Fetch 单独列为"每 1,000 次成功请求"的计价项（该页同时说明通过其 Harness / Claude Code / Codex 调用时的计费生效时间，核验于 2026-10-31）。这类费用与 Token 无关，一次任务检索 20 次就是 20 次的钱，跟你用哪个模型没关系。

自建工具（查数据库、跑代码、调内部 API）没有外部计费，但有算力与延迟成本。做预算时把工具调用次数单独统计，不要混进 Token 账里，否则优化方向会跑偏：一次任务的 Token 成本降了 30%，但工具调用次数翻倍，总账可能是涨的。

## 四、失败与重试：最容易被低估的一块

Agent 的费用不是"成功任务的成本"，而是"所有尝试的成本之和"。这里有两次放大。

**第一次放大：单步重试。** 单步成功率 `q`、最多重试 3 次时，期望请求数是 `1 + (1−q) + (1−q)²`。`q = 0.9` 时为 1.11，`q = 0.8` 时为 1.24，`q = 0.5` 时为 1.75。

**第二次放大更致命：任务级重试。** 一个任务需要 `n` 步全部成功，单步成功率 95% 听起来很好，但：

```
任务成功率 ≈ q^n = 0.95^12 ≈ 0.54
```

也就是说，一个 12 步的任务有接近一半的概率中途失败。如果产品体验要求"失败后重跑直到成功"，期望尝试次数是 `1/0.54 ≈ 1.85`，成本直接乘以 1.85；30 步的复杂任务，`0.95^30 ≈ 0.21`，期望尝试 4.7 次。

这个结论对预算的影响远大于选模型：**把单步成功率从 95% 提到 98%，30 步任务的成功率从 21% 提到 55%，期望重试次数从 4.7 降到 1.8**。提高可靠性的投入，在 Agent 场景里通常比降价更值钱。

（这里的乘法模型假设各步独立，现实中错误往往相关——同一个提示词缺陷会让每一步都偏，实际成功率会更低。所以把它当作乐观上界。）

## 五、三个场景的完整算例

把上面三块合起来，给一个可以直接代入的计算函数。示例参数调用的是第二节的数值，`失败率` 指任务级重试的期望倍数：

```ts
export interface AgentTaskModel {
  steps: number;
  fixedPerStep: number;      // S：系统提示 + 工具定义
  growthPerStep: number;     // o：每步输出 + 工具返回
  toolCalls: number;         // 工具执行次数（模型外计费项）
  taskSuccessRate: number;   // 0~1，通常按 q^steps 估
}

export interface TokenUsage {
  input: number;
  output: number;
}

/** 返回单任务的期望 Token 消耗（已含任务级重试） */
export function estimateTaskUsage(m: AgentTaskModel): TokenUsage & { attempts: number } {
  const baseInput = m.steps * m.fixedPerStep + (m.growthPerStep * m.steps * (m.steps - 1)) / 2;
  const baseOutput = m.steps * m.growthPerStep;
  const attempts = m.taskSuccessRate > 0 ? 1 / m.taskSuccessRate : Infinity;
  return {
    input: Math.round(baseInput * attempts),
    output: Math.round(baseOutput * attempts),
    attempts: Number.isFinite(attempts) ? Number(attempts.toFixed(2)) : Infinity
  };
}

/** 由单步成功率推算任务成功率，便于替换假设 */
export function taskSuccess(stepSuccess: number, steps: number): number {
  return Math.pow(stepSuccess, steps);
}
```

代入三组示例假设（单价请用 [模型库](/models/) 的核验价代入，本文不列价格）：

| 场景 | 步数 | 单步成功率 | 任务成功率 | 期望尝试 | 期望输入 Token | 期望输出 Token |
|---|---|---|---|---|---|---|
| 简单 | 4 | 0.98 | 0.922 | 1.08 | 8,424 | 1,296 |
| 典型 | 12 | 0.95 | 0.540 | 1.85 | 93,240 | 8,880 |
| 复杂 | 30 | 0.95 | 0.215 | 4.65 | 1,259,000 | 62,775 |

简单场景验算：`(4×1500 + 300×6) × 1.08 = 7,800 × 1.08 = 8,424`。复杂场景：`(270,750) × 4.65 ≈ 1,259,000`。

看到复杂场景的那个数字，就能理解为什么很多 Agent 产品上线后账单超出预期十倍——不是单价选错了，而是"30 步 × 21% 成功率 × 每次重跑"这三件事乘在了一起。

## 六、从单任务到月账单

拿到单任务期望消耗后，月度成本只需要三个业务参数：

```
月调用量 = 日活用户 × 人均任务数 × 30
月 Token = 月调用量 × 单任务期望 Token
```

但要注意"月调用量"的口径：用户点了两次、重试了一次、后台补偿任务又跑了一次，这些都会产生调用。用**网关侧的请求计数**而不是业务侧的成功任务数来估，否则永远偏低。

按场景分层估算比"取一个平均值"有用得多。举个假设的负载结构：简单任务占 70%、典型 25%、复杂 5%。代入第五节的期望输入 Token（8,424 / 93,240 / 1,259,000），加权平均约 92,000——其中那 5% 的复杂任务贡献了约 63,000，也就是**六成七的成本来自占比最小的那一档**。只看"平均每个任务多少钱"，会完全看不出成本出在哪一档。

## 七、把失控挡在结构里

Agent 的成本风险有一半来自"异常运行"：模型不断重复调用同一个工具、在两个状态之间来回跳、把工具返回的错误当成新输入继续尝试。三种止损设计必须做：

**步数上限**：`max_steps`，超过就返回部分结果。这是最基本的保险丝，没有它，一个坏提示词可以在一夜之间跑掉一个月预算。

**预算上限**：按任务累计 Token 或金额设阈值，达到 80% 时警告、100% 时终止。金额口径比 Token 口径更直观，但需要一张模型到单价的映射表——这正是"请求级成本记录 + 预算控制"要做的事，也说明成本核算不该等到月底做。

**循环检测**：连续两次调用的工具名与参数完全相同、或者工具返回的内容与上一轮几乎一致，就判定为循环。这类检测几行代码就能实现，收益是防止最坏情况：

```ts
export function looksLikeLoop(recent: Array<{ tool: string; argsHash: string }>, window = 3): boolean {
  if (recent.length < window) return false;
  const last = recent[recent.length - 1];
  const same = recent.slice(-window).filter(r => r.tool === last.tool && r.argsHash === last.argsHash).length;
  return same >= window;
}
```

## 八、一个容易被忽略的优化：前缀天然稳定

Agent 的请求形态对缓存极其友好：每一步都在上一步的末尾追加内容，前缀单调增长。主流的前缀缓存机制正是按"请求边界处的前缀单元"命中，多轮追加正是它最容易命中的形态（机制细节与命中条件见 DeepSeek 的 Context Caching 文档，2026-10-31 核验）。

这意味着 Agent 的输入成本有很大一块可以压——前提是**不要把变化的东西塞进中间**：每步都重新生成的工具列表、每步都更新的"当前时间"、每次重排的记忆片段，都会让前缀失效。收益条件的定量分析见本系列另一篇关于缓存优化的指南（目前仍在草稿阶段）。

- 单次请求的 Token 计价口径（输入输出分价、分档、峰谷）：[如何计算 LLM API 成本](/guides/llm-api-cost/)；

最后一句话作为收尾：Agent 成本的可控性，八成来自"步数"和"成功率"这两个非价格变量。先测这两个数，再谈选型。
